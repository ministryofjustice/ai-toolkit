# GOV.UK Design System

Use this skill alongside the active workflow, not instead of it. For Forge
journeys, also use the `forge-development` skill.

Before designing or implementing a UI, or writing a specification or ticket
for UI implementation, check the GOV.UK Design System
[patterns](https://design-system.service.gov.uk/patterns/) and
[components](https://design-system.service.gov.uk/components/) for guidance
relevant to the user need. Read the applicable guidance, including when to use
and not use it, examples, accessibility and research considerations. Do not
select a pattern or component based on its name alone.

The lists below reflect the Design System indexes checked on 26 November 2026.
The indexes are authoritative and may change; check them for additions or
changes rather than relying solely on these lists.

## Apply the guidance

Read the consuming project's `TECHNOLOGY.md`, relevant specification, ticket,
ADRs and existing UI conventions when available. Prefer an appropriate existing
GDS pattern or component to a bespoke design, adapting it to the service and
its users. Check how it can be implemented with the project's technology and
installed dependencies; do not assume Forge or a particular GOV.UK Frontend
version is in use, or invent APIs.

In specifications and tickets, identify the relevant patterns and components,
link to their guidance and describe the behaviour and accessibility requirements
needed for the user need. Do not prescribe an implementation unsupported by
the project context. If guidance is unsuitable or a departure is needed, explain
why and record material decisions in the artefact.

If the guidance is unavailable, say so and use verified local documentation
and project code where possible. Do not claim to have checked guidance that
could not be accessed; flag material uncertainty.
